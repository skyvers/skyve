# Sign Out Everywhere: Token Cleanup on Disable and Delete, and Sign Out of All Other Sessions

## Goal

1. **6a, token cleanup.** When a user is disabled or deleted, all of that user's remember-me tokens go and their sessions end, so re-enabling the user does not bring old cookies back to life and a user created later with a deleted user's name is not signed in by the old cookies.
2. **6b, sign out everywhere,** as Google, Microsoft, GitHub and Slack have it:
   - **Self-service.** On the user's account page (`admin.UserAccount`, My Current Sessions), **Sign out of all other sessions** ends every other device, and not this browser.
   - **Administrator.** On `admin.User`, **Sign out everywhere** ends every device of that user.
   - The user menu's **Sign out** stays as it is (this device only; see `plan_remember_me_per_device.md`).

## Context (verified)

- **Remember me storage.** `ADM_UserToken` rows are keyed by `userName`, which holds `customer/userName` (`SkyveRememberMeTokenRepository.createNewToken`, as `Authentication.getName()` gives it), and `series`. The `remember` cookie holds Base64 of `series:token`, **each part URL-encoded** (Spring's `AbstractRememberMeServices.encodeCookie`), so a series such as `0PjFbQ0J05e+YG2CIMTo7A==` is `0PjFbQ0J05e%2BYG2CIMTo7A%3D%3D` in the cookie. Nothing needs adding to the schema.
- **Sessions.** `StateUtil` (`skyve-ext/.../cache/StateUtil.java`) keeps a set of session ids per user bizId in the session cache. A session ends when it is no longer in its user's set: `WebUtil.processUserPrincipalForRequest` (`skyve-web/.../WebUtil.java` line 108) and `getValidatedSessionUser` (line 179) call `checkSession`, invalidate the session and throw `SessionEndedException` (the expired page). Sessions are therefore ended lazily, at their next request. `StateUtil.removeSessions(userId)` removed all of a user's sessions; there was nothing that kept one. `SkyveSessionListener.sessionDestroyed` unregisters a session when it ends by itself.
- **How "disabled" is represented.** `inactive` (on `admin.UserProxy`, which `admin.User` extends) and `activated` (`User.xml`, default true). `SkyveSpringSecurity`'s user queries read `enabled` as `not ifNull(inactive, false) and ifNull(activated, true)`, and Spring refuses to sign in (or auto-login from a cookie) a user that is not enabled. `LocalDataStoreRepository` refuses an inactive user's roles. Disabled therefore means `inactive = true` or `activated = false`.
- **Every path that disables or deletes a user, before this change.**

  | Path | Where | Before | After |
  | --- | --- | --- | --- |
  | Save the User (edit view: Inactive, Account Activated; REST/JSON `admin.User`; any code that saves a `User`) | `UserBizlet.postSave` | tokens and sessions removed only for a password change | also removed when the user is saved disabled (`inactive` or not `activated`) |
  | Delete the User (edit view, User list, REST/JSON, a Tag's delete, code) | `UserBizlet` had `preDelete` only | rows stayed, keyed by `customer/userName` | `postDelete` removes the user's tokens and sessions |
  | Rename the User (`userName` changed on a saved user) | `UserBizlet.preSave` and `postSave` | rows stayed under the old name; a user created later with that name was signed in by them | the old name's tokens, and the user's sessions, are removed (not in the brief: the same hazard as delete) |
  | Self-registration, `CreateUsers`, `InviteUsers`, `SubscriptionService` | create users | nothing to remove | unchanged (`SelfRegistration` creates users not `activated`; `postSave` then removes zero rows) |
  | Bulk SQL (Data Maintenance restore, truncate) | raw SQL | nothing | unchanged: those bypass bizlets by design |
  | `admin.UserProxy` | mapped superclass with no Bizlet or view | n/a | not covered: nothing edits a user through it, but a `_RU_C` role could update `inactive` through the REST API for that document |

  A disabled user could not sign in by cookie anyway (Spring checks `enabled`), so the cleanup closes the re-enable and same-name cases, and ends their live sessions.
- **The action paths.** A button for an action with `inActionPanel="false"` needs an `<action>` in the view's `<actions>` and a `<button action="...">` in its body (as `ResendActivation`). The renderers resolve the action's `confirm` through `Action.getLocalisedConfirmationText()` (`Util.i18n`), in SmartClient (`ViewJSONManipulator`) and PrimeFaces (`FacesViewRenderer`), so one view XML serves both. `<button>` has no `visible` or `invisible` attribute in `view.xsd`: its visibility is its action's `visible` condition. The action privilege is a `<action name="..."/>` in the role's `<document>` privilege in `admin.xml`.
- **The current browser.** An action runs in the browser's request: `EXT.getHttpServletRequest()` gives its cookies (the `remember` cookie, `SpringSecurityConfig.REMEMBER_ME_PARAMETER`) and `getSession(false)` its session. Both renderers' action requests carry them (verified in a browser, below).

## Locked decisions

1. **6a: disabled means `inactive` or not `activated`,** and the cleanup runs in `UserBizlet.postSave` whenever a user is saved in that state (idempotent; one delete of at most a few rows, and only for a disabled user), and in `postDelete`. It removes **all** of the user's tokens (`removeUserTokens(persistence, customer/userName)`, in the save's transaction) **and ends all their sessions** (`StateUtil.removeSessions`). Why sessions too: the user is disabled or gone, so a session that keeps working on its cached `User` object is the same hole as a cookie that does; it is what a password change does already; and it is safe, because the sessions end at their next request and the user cannot sign in again. When an administrator disables themself, their own session ends at its next request: that is right for a disabled user.
2. **6a also covers a rename** (old name's tokens and the user's sessions), through a stash value set in `preSave` from `originalValues()`, like the password change. Beyond the brief; flagged for Mike.
3. **6b self-service** (`admin.UserAccount.actions.SignOutOtherSessions`): the user is always the signed-in user, never a parameter. It removes all of the user's tokens except the series in this request's `remember` cookie (all of them if there is no usable cookie), and ends all the user's sessions except this request's session (all of them if the request has none). It asks first (`confirm`), then shows "Signed out of N other session(s)." or "You had no other sessions to sign out of." N is the larger of the sessions ended and the token series removed: one device usually has one of each, so the sum would count it twice. The sessions list in the tab refreshes. Granted to `AppUser`, `BasicUser` and `ViewUser` (the roles that have `UserAccount`).
4. **6b administrator** (`admin.User.actions.SignOutEverywhere`): removes all of the user's tokens and ends all their sessions, after a confirmation, then says "{user} has been signed out everywhere.". Granted to `SecurityAdministrator` (the privilege that manages users: its `User` privilege is `CRUDC` and it has `GeneratePassword`, `ResendActivation`), shown with the `securityAdministrator` condition. The action also checks, server side, that the caller is a `SecurityAdministrator` and of the user's customer, and throws `AccessException` otherwise. Unsaved users have nothing to sign out (a message). The tokens are keyed by the saved name, so a user name typed into the form and not saved is ignored.
5. **An administrator who signs out themself** keeps this browser's session and Remember me series, as the account page does, with the message "Signed out everywhere else. This session stays signed in." Chosen over ending the current session (which would end the request that is answering, to the expired page) or refusing (which leaves no way to do it from the user view). The account page does the same job without the administrator role.
6. **The user menu keeps plain Sign out.** Nothing is added to the avatar or user menu.
7. **Both renderers, one view.** The new buttons are in `UserAccount/views/edit.xml` and `User/views/edit.xml`, which SmartClient and PrimeFaces both render. Nothing differs.
8. **`StateUtil.removeOtherSessions(userId, keep)`** (new, atomic like `removeSession`): unregisters all the user's session ids but `keep`'s and returns how many it removed; `keep` is not added if it is not registered.
9. **`SkyveRememberMeTokenRepository.removeOtherUserTokens(persistence, userName, keepSeries)`** (new, with `getRemoveOtherUserTokensSql`/`setRemoveOtherUserTokensSql`; default `delete from ADM_UserToken where userName = ? and series <> ?`): returns the number removed; a `null` series removes all of the user's tokens.
10. **`SkyveRememberMeServices.extractSeries(request, cookieName)`** (new, static): the series of this browser's cookie, URL-decoded, or `null` for no cookie, another cookie, bad Base64 or a cookie not of the form `series:token`. `SpringSecurityConfig.REMEMBER_ME_PARAMETER` becomes public for it. An app that renames its remember-me cookie should not offer the account button (no cookie found would remove all of the user's tokens).
11. **One helper, `modules.admin.User.SignOut`** (`everywhere`, `otherDevices`), used by `UserBizlet` and both actions.
12. **i18n.** New keys in `i18n.properties` and, as the repo's earlier changes did for new UI strings (`ui.dialog.*`, the Account page), translated in `i18n_de`, `i18n_fa`, `i18n_hi` and `i18n_vi` (`i18n_ar` has only a few `ui.*` keys, so it is left as it is). The `{0}` messages avoid apostrophes (they are formatted).
13. **No schema change.** Out of scope: two-factor remember-me (another branch), purging expired token rows.
